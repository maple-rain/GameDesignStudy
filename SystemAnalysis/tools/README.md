소울 결정 5종의 **체결가와 거래 속도**를 매일 쌓는다.
수집한 데이터는 `data/` 아래 월별 CSV로 남는다.

<a href="https://developers.neople.co.kr" target="_blank">
<img src="../images/neople-openapi.png" alt="Neople 오픈 API" />
</a>

이 폴더의 스크립트와 `data/` 아래 CSV는 **네오플 오픈 API 서비스**의 결과 데이터를 이용해 만들어졌습니다.
결과 데이터의 저작권 등 제반 권리는 ㈜네오플 또는 제3자에게 있습니다.
— [이용 약관](https://developers.neople.co.kr/contents/policy) 제6조 · [BI 가이드](https://developers.neople.co.kr/contents/bi)

### 무엇이 허용되는지 먼저 확인했다

> **Q. 오픈API 데이터를 수집, 가공해서 서비스를 제공해도 되나요?**
> 이용약관에 위배 되지 않는 범위 내에서 **캐시 형태의 API 데이터 수집 및 재가공 서비스를 허용**하고 있으며
> API 서비스 이용 중단(제재 포함)시에는 API 서비스를 이용해 얻은 데이터 및 추가 생산물에 대해서 **모두 삭제**하여야 합니다.
> — [FAQ · 이용가이드](https://developers.neople.co.kr/contents/faq?category=3)

약관 제5조 제5항의 `본 약관에서 허용한 범위`가 무엇인지는 약관 본문만으로는 알 수 없었다.
**FAQ가 그 범위를 명시하고 있어 이 수집기의 형태를 거기에 맞췄다.**

### 호출량

공식 허용량과 실제 사용량이다. `※ 최대 허용량은 사전 고지 없이 변경될 수 있으므로 수시로 확인하시기 바랍니다.`

| 기준 | 1초 허용 | 1분 허용 | **이 수집기** |
|---|---|---|---|
| APIKEY | 500건 | 30,000건 | 2시간마다 10건 |
| 요청 IP | — | 50,000건 | 〃 |

아이템 5종 × 엔드포인트 2개 = 실행당 10회, 호출 간 0.5초를 둔다. 하루 120회.
**1분 허용량의 0.04%다.**

### 남기는 데이터의 형태

원본 응답을 그대로 덤프하지 않는다.
받아온 내역은 메모리에서 집계한 뒤 버리고, 중앙값·건수·시간 폭 같은 **집계값**만 남긴다.
해당 엔드포인트의 응답에는 판매자·구매자·캐릭터명 등 회원 정보에 해당하는 항목이 **처음부터 없다.**

## 왜 만들었나

시세 사이트(던파나우 · 던파파워 · 던프라이스)는 **최대 1주일치만 보여준다.**
웨이백 머신에 남은 스냅샷은 월 1회 해상도이고 가격 숫자가 없다.

과거를 복원할 수 없으면 **지금부터 만드는 수밖에 없다.**

## 무엇을 어떻게 재는가

| 엔드포인트 | 주는 것 | 읽는 것 |
|---|---|---|
| `/df/auction-sold` | 최근 체결 내역 (최대 100건 / 1개월) | **수요** |
| `/df/auction` | 현재 등록 매물 | **공급** |

`auction-sold`가 100건까지만 준다는 제약을 역이용한다.

```
100건이 쌓이는 데 걸린 시간 폭  →  시간당 체결 건수  →  거래 속도
```

태초 소울 100건이 30분 만에 쌓이고 유니크 소울 100건이 3일 걸린다면,
그 시간 차이가 곧 거래량 차이다. **API가 거래량을 직접 주지 않아도 잴 수 있다.**

## 왜 가격만으로는 안 되는가

앞선 분석에서 한 번 틀렸다.
유니크 소울이 다른 등급보다 58% 비싼 것을 보고 수요가 있다고 읽었는데, 실제로는 반대였다.
아무도 사지 않아 걸러진 매물만 남아 있던 호가였다.

**경매장에 뜨는 값은 팔린 값이 아니라 부르는 값이다.**
그래서 이 수집기는 등록가와 체결가를 나눠 기록한다.

→ [던전앤파이터 중천 파밍 구조](../DNF_JungCheon_Farming.md)

## 쓰는 법

### 1. API 키 발급

[developers.neople.co.kr](https://developers.neople.co.kr) 에 가입하고 애플리케이션을 등록하면 apikey가 나온다.

### 2. 키 파일 만들기

이 폴더에 `apikey.txt` 를 만들고 키만 한 줄로 넣는다.

```
발급받은_키_문자열
```

**이 파일은 저장소에 올리지 않는다.** `.gitignore`에 등록되어 있다.

### 3. 응답 구조 먼저 확인

문서와 실제 필드명이 다를 수 있으므로 처음 한 번은 원본을 본다.

```bash
python dnf_collect.py --raw
```

`soldDate` `unitPrice` `count` 같은 필드가 실제로 어떤 이름인지 확인하고,
다르면 `dnf_collect.py`의 `collect()` 안에서 키 이름을 고친다.

### 4. 수집

```bash
python dnf_collect.py
```

`data/soul_YYYYMM.csv` 에 한 줄씩 추가된다.

### 5. 자동 수집

**주 수집기는 GitHub Actions다.** 워크플로는 [`.github/workflows/dnf-collect.yml`](../../.github/workflows/dnf-collect.yml).

PC를 켜 두는 것에 의존하지 않기 위해서다.
API는 최근 100건까지만 주기 때문에, 꺼져 있던 동안 체결된 건은 다음에 켜도 이미 밀려나 있다.
**놓친 구간은 나중에 채울 수 없다.**

| | 로컬 작업 스케줄러 | GitHub Actions |
|---|---|---|
| PC가 꺼져 있으면 | **못 돈다** | 돈다 |
| 시각 정확도 | 정확 | 수 분 ~ 수십 분 밀릴 수 있다 |
| 결과 | 로컬 CSV | 저장소에 자동 커밋 |

두 수집기가 같은 파일을 건드리면 git에서 매번 충돌하므로 **파일명을 나눴다.**

```
로컬   data/soul_YYYYMM.csv        .gitignore 처리. 백업용
CI     data/soul_YYYYMM_ci.csv     저장소에 커밋되는 본 자료
```

#### 키 등록

저장소 `Settings` → `Secrets and variables` → `Actions` → `New repository secret`

```
Name    DNF_API_KEY
Secret  발급받은 키
```

**키는 저장소 파일에 절대 넣지 않는다.** 스크립트는 환경변수 `DNF_API_KEY`를 먼저 보고,
없을 때만 로컬 `apikey.txt`를 읽는다.

#### 첫 실행 확인

`Actions` 탭 → `DNF 시세 수집` → `Run workflow` 로 수동 실행해 본다.
성공하면 `data/soul_YYYYMM_ci.csv` 가 커밋된다.

> 공개 저장소의 예약 워크플로는 **60일간 저장소에 활동이 없으면 자동으로 중지된다.**
> 이 수집기는 스스로 커밋을 남기므로 해당되지 않지만, 저장소를 오래 방치할 때는 확인이 필요하다.

#### 로컬 병행 (선택)

Windows 작업 스케줄러에 함께 등록해 두면 백업이 된다.

```
프로그램      pythonw
인수          "<이 폴더>\dnf_collect.py"
시작 위치     <이 폴더>
트리거        2시간마다 반복
설정          "예약 시작 시간을 놓친 경우 가능한 대로 작업 시작" 을 켤 것
```

마지막 줄을 켜지 않으면 **PC가 꺼져 있던 동안의 실행은 그냥 건너뛴다.**

## 기록되는 값

| 열 | 뜻 |
|---|---|
| `수집시각` | 실행한 시각 (KST) |
| `체결건수` | 이번에 받아온 체결 내역 수 (최대 100) |
| `체결수량합` | 그 건들의 수량 합계 |
| `체결가_중앙` | 개당 체결가의 중앙값 |
| `체결가_최저` | 개당 체결가의 최저값 |
| `체결구간_시간` | 가장 오래된 체결과 가장 최근 체결 사이의 시간 |
| **`시간당_체결건수`** | **거래 속도. 이 수집기의 핵심 지표** |
| `매물_최저가` | 현재 등록된 매물의 최저 단가 |
| `매물_수량` / `매물_등록수` | 현재 공급 |

중앙값을 쓰는 이유는 최저가 하나가 시장을 대표하지 못하기 때문이다.
유니크 소울에서 최저가만 보고 잘못 읽은 것이 그 사례다.

## 하루 2회를 권하는 이유

거래가 활발한 등급은 100건이 몇 시간 만에 찬다.
하루 한 번만 돌리면 그 사이의 체결을 놓치고, `체결구간_시간`이 항상 짧게만 나온다.

반대로 거래가 없는 등급은 100건에 며칠이 걸리므로 중복이 쌓인다.
중복은 나중에 `수집시각`과 체결 내역으로 걸러낸다.

## 한계

- 100건 제한 때문에 **거래가 매우 활발한 등급은 실제 거래량을 과소 집계**한다.
  시간당 체결 건수는 하한값으로 읽어야 한다.
- 서버별 구분이 없다. 전체 서버 합산인지 확인이 필요하다.
- 과거는 채울 수 없다. 이 수집기는 **오늘 이후**만 만든다.

## md2pdf.py — 분석서를 인쇄용 PDF로

분석서 `.md` 하나를 A4 PDF 로 뽑는다. 산출물은 `SystemAnalysis/pdf/` 에 둔다.

```bash
python SystemAnalysis/tools/md2pdf.py SystemAnalysis/DNF_TropicalPackage_BM.md
chrome --headless=new --disable-gpu --no-pdf-header-footer   --print-to-pdf=SystemAnalysis/pdf/DNF_TropicalPackage_BM.pdf   file:///.../SystemAnalysis/DNF_TropicalPackage_BM.html
```

`--title "탭 제목"` 을 주지 않으면 문서의 첫 `#` 제목을 쓴다. 파일은 `utf-8-sig` 로 읽는다
(`DNF_JungCheon_Farming.md` 에 BOM 이 있고, 그대로 읽으면 첫 줄이 제목으로 잡히지 않는다).
중간 산출물 `.html` 은 `.gitignore` 에 있다.

정한 것 다섯.

| 항목 | 값 | 이유 |
|---|---|---|
| 본문 폰트 | 맑은 고딕 | 윈도우 기본. 별도 설치 없이 재현됨 |
| 코드블록 폰트 | 굴림체 | **한글이 영문·숫자의 정확히 2배 폭.** 계산 블록의 숫자 정렬이 유지됨 |
| 개행 단위 | 부(部)만 새 쪽 | 장마다 개행하면 장 끝 여백이 커짐 (49쪽 → 43쪽) |
| 목차 | 언제나 별도 쪽 | 부가 있으면 첫 부의 `break-before` 가 목차 쪽을 닫고, 부가 없으면 `.toc` 에 `break-after` 를 건다. 둘을 같이 걸면 빈 쪽이 생김 |
| 인용 블록 | 원문 행 그대로 | markdown 이 연속 `>` 행을 한 문단으로 합치는 것을 강제 개행으로 막음 |

표는 행 단위로 쪼개지고 머리행이 다음 쪽에 반복된다. 코드블록은 쪼개지지 않는다.

던파 세 편 실측.

| 문서 | 쪽 | 빈 쪽 | 코드 최대폭 | 한글 |
|---|---|---|---|---|
| 중천 파밍 | 10 | 0 | 80 | 4,523자 |
| 소울 시세 | 14 | 0 | 79 | 7,451자 |
| 트로피컬 BM | 43 | 0 | 98 | 25,007자 |

세 편 모두 1쪽 제목·머리말 / 2쪽 목차 / 3쪽부터 본문이다 (트로피컬은 목차가 2~3쪽).
코드블록 폭 한도는 116 이다 — 8.4pt 굴림체로 본문폭 180mm 에서 `pre` 여백을 뺀 값이고,
한글은 2로 센다.
